# GraphRAG 五个真实缺口的严格修复

## 0. 目标与判定标准

上一轮审计发现 5 个**代码可修复**的缺口（第 5 项生产压测属环境依赖，不在本计划内强行"造假通过"）。
本计划逐一给出修复 + **能真正证伪的测试**（现有测试之所以没抓到，是因为它们测的是自己的 fixture）。

修复完成后应满足：**不设任何非默认值的生产配置下，设计要求的行为真的生效**；**消融 CSV 记录的是真正发出去的请求**；**答案指标要么真产出、要么在报告中明确标注未产出**。

## 1. 已核实的五个缺口（含精确证据）

### G1 — 图扩展成本控制在生产默认配置下全部空转（阻断）

- `RetrievalProperties.java:114` `@Inject("${retrieval.graph.sample-rate:1.0}")` → `graphSampleRate = 1.0D`
- `RetrievalProperties.java:116` `min-marginal-yield:0.0`
- `application.yml:64-67` 分别为 `1.0 / 0.0 / 0.0 / 0.0`
- `GraphRetriever.java:483-497` `sampledEdge()`: `if (config.getSampleRate() >= 1.0) return true;` → 采样从不裁剪
- `graphRelationPriorities = 空 LinkedHashMap`（`RetrievalProperties.java:122`），`application.yml` 无对应键 → 所有边优先级同为 1.0，`GraphRetriever.java:504,529` 退化
- 后果：`MARGINAL_YIELD_LIMIT` 与 `LOW_ASSOCIATION_SCORE` 在生产中不可达
- **测试为何没抓到**：`GraphAssemblyIntegrationTest.properties()`（`:172-177`）显式把所有值重置为惰性值，然后每个用例只覆盖其中一个；`defaultPropertiesKeepTheGraphChannelProductive`（`:151`）只断言"非空"，正好与"默认值惰性"相容

**不一致点（额外发现）**：`RetrievalProperties.java:118,120` 的 `@Inject` 默认值是 `0.01 / 0.05`，而 `application.yml:66-67` 是 `0.0 / 0.0`。两处默认值已经漂移。

### G2 — 消融 CSV 记录的是消融前 mode（阻断，且污染实验结论）

- `benchmark_http.py:38,41` `apply_ablation` 把 `no-anchor`→`BM25_ONLY`、`high-degree`→`GRAPH_ONLY`
- `benchmark_http.py:267`（逐行）与 `:361`（汇总）写的是 `config['mode']` / `METHOD_CONFIG[method]['mode']`，即**消融前**的值
- 实测产物 `ablations/2wiki/no-anchor.csv` 记为 `FIXED_HYBRID`，而实际请求是 `BM25_ONLY`；`meanEvaluatedBM25 = 0.0` → 该行 recall `0.0` 是**空转**，不是"BM25 命中不了"
- `test_ablation_shapes_only_the_wire_request`（`test_http_benchmark.py:151-180`）断言了 wire body 被改写，但**没有任何测试断言 CSV/row 记录改写后的值** → 漏洞正来自此处
- 上一轮只修了 `candidateLimit`（`benchmark_http.py:262-264` 注释即为此），漏了 `mode`

### G3 — `answerExactMatch` / `answerF1` 恒为空（DoD 表却标"达成"）

- `benchmark_http.py:259` `predicted_answer = response.get('answer')` —— `/api/v1/retrievals` 响应**从不含 `answer`** 字段
- 于是 `:278-281` 的 `if isinstance(predicted_answer, str)` 恒假 → `exactMatch`/`f1` 恒 `None` → `_mean_metric` 返回 `None` → CSV 空
- 实测：两份全量 CSV 的 `answerExactMatch` 与 `answerF1` 均 `nonempty=0/6`
- 答案能力已存在但没被 runner 消费：`GeaFlowMemoryServer.java:179` 已有 `POST /api/v1/answers`
- `relationPathHit`：2Wiki 为 `0.0`（有效但全零）；HotpotQA 为空 —— 需查明是 gold 无 relation 还是路径匹配失效

### G4 — `/ready` 缺少"artifact 被破坏 → 503"的契约测试

- 代码已修：`GeaFlowMemoryServer.java:337-347` 走 `readiness(...)` 分项
- 缺的是**真正的破坏性契约测试**（删/截断 `vector.bin` 后打 HTTP 断言 503 + 原因），现有 `ReadinessReportTest` 只测 report 对象字段

### G5 — 生产压测 acceptance 仍 FAIL 且无 SLO（**不在本计划内强行关闭**）

- `production-load/20261018T132744Z/acceptance.json`: `passed=false, latencySloConfigured=false`
- `production-load/smoke2/acceptance.json`: `passed=true` 但 `latencySloConfigured=false`（无阈值，不能证明延迟）

## 4. 风险与边界

- **改默认 `sample-rate=0.5` 会改变检索结果与既有基准数字**。缓解：先只改 `application.yml`/`@Inject` 默认值并补齐测试，**重跑 smoke 对比 evidence 数量变化**；若变化过大（如 recall 明显下降），把 `sample-rate` 保持 `1.0` 但在文档中明确"采样默认关闭，需通过环境变量启用"，**同时保留另外四项为非惰性**，避免"默认为空转"却不自知。

### 新发现的 bug

**N1 — 消融请求全部被 HTTP 400 拒绝，却被记成"召回 0"（严重，污染所有消融结论）**

- 现象：`apply_ablation` 把 mode 改写为 `BM25_ONLY`/`GRAPH_ONLY`，但**保留了 `queryVector`**；
  服务端返回 `UNSUPPORTED_OPTION: queryVector is not supported for mode BM25_ONLY`。
- 4 个条件 × 240 请求**全部失败**，runner 的重试循环把失败也写入行，汇总时平均成 `recall 0.0` +
  `meanEvaluated*=0`。
- 这就是上一轮「消融 row 的 `meanEvaluated*=0` 说明空转」的**真正原因**，比原先判断更具体：
  不是配置缺省，而是请求根本没被接受。

### 过程中发现并修复的 1 个 bug

**压测夹具的连接复用缺陷（会伪造 FAIL）**

- 第一次 SLO 运行 `20261104T092500Z` 判 `passed: false`，但查证后 **0 次 SLO 超标**
  （p95 最高 57.3 ms），5 个失败阶段的真实原因是共 10 次 `transportFailure`：
  `RemoteDisconnected: Remote end closed connection without response`。
- 根因：`HttpWorker` 按线程复用 keep-alive 连接，服务端 smart-http 空闲超时会关闭它们；
  客户端拿到已关闭的 socket 发请求即失败，服务端同时记 `IOException: writeBuffer has closed`。
- 若不修，会得出"服务不达标"的错误结论。修复：仅对**失效连接**重连一次并重试，
  其他传输错误不重试；重试成功清除 `error` 并标记 `staleConnectionRetried`；
  重试仍失败则记录为失败而**不抛异常**（抛异常会中断整个压测）。
- 测试：`test_stale_pooled_connection_is_retried_once`、
  `test_retried_request_still_fails_when_the_reconnect_also_fails`、
  `test_non_stale_transport_error_is_not_retried`，回退修复 → 2 项 RED。
- 旧运行已保留并在 `PRODUCTION_LOAD.md` 中如实标注为"夹具 bug 证据，不是延迟失败"。
