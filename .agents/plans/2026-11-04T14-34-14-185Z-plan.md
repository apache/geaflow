# 排查并妥善处理 Adaptive Hybrid 设计中的风险魔法数字

## 1. 目标与假设

**目标**：找出那些会改变检索行为、却既不可配置也不进入 trace/metadata 的数值常量，并按风险等级妥善处理。

**处置原则**（按优先级）：
1. **配置化**：进入 `RetrievalProperties`（`@Inject`），带范围校验与默认值。
2. **可观测**：写入 trace 或 build metadata，使每次运行可复现、可解释。
3. **文档化**：若确实不应暴露，则加 Javadoc 说明取值依据与量纲。

**关键假设**：默认值保持现状（除已确认错误的之外），确保已有 benchmark 结果不会因本次改动而漂移。

**范围排除**：
- 设计文档中的 JSON 示例值（`0.94`、`2.18`、`0.61`、`0.84` 等）不是常量。
- Lucene `8.11.2` 是依赖版本。
- `maxHop <= 2` 已由 `GraphRetrievalConfig.build()` 强制校验，属已落实的硬约束。
- `serialVersionUID`、`EMPTY` 数组、`FNV_PRIME`、`CHARACTERS_PER_TOKEN` 等不改变检索语义。

## 2. 关键发现（已核实）

### 2.1 我上一轮引入的新魔法数字（最高优先级）

`DeterministicRulePolicy` 中 7 个常量无配置入口，而实测证明它们对质量影响极大
（仅把 graph/text 权重从 `1.0/1.25` 改为 `2.0/0.25`，2Wiki MRR 从 0.1019 升到 0.4747）：

| 常量 | 值 | 位置 |
|---|---|---|
| `GRAPH_FIRST_GRAPH_WEIGHT` | 2.0 | `DeterministicRulePolicy.java:48` |
| `GRAPH_FIRST_TEXT_WEIGHT` | 0.25 | `:49` |
| `GRAPH_PROBE_SHARE` | 0.4 | `:56` |
| `LEXICAL_BM25_WEIGHT` / `LEXICAL_VECTOR_WEIGHT` | 1.25 / 0.85 | `:33-34` |
| `SEMANTIC_BM25_WEIGHT` / `SEMANTIC_VECTOR_WEIGHT` | 0.85 / 1.25 | `:36-37` |

### 2.2 `rankConstant = 60`：不可配置，且是量纲问题的根源

- 定义于 `fusion/WeightedRrfConfig.java:23` 的 `DEFAULT`，构造点全部使用它。
- 它决定了所有融合分数的量纲（`w / (60 + rank)`），因而决定了 `first_stage_score_gap` 的
  实际范围（实测中位 `0.00055`）。
- **这正是上一轮 `highScoreGap` 默认值 `0.20` 撞车的根因**：阈值与量纲不匹配。

### 2.3 `CASCADE_*` 五件套：只在 fallback 路径生效（风险较低）

`RecallPlan.java:42-46`：
```java
CASCADE_MIN_BUDGET = 5;  CASCADE_PROBE_MAX = 10;
CASCADE_PROBE_MIN = 2;   CASCADE_PROBE_DIVISOR = 8;
```

**已核实**：自适应模式下 `RecallService:663-667` 通过 `orderedBudgets(routingPlan)` 显式传入
通道预算，`CASCADE_*` 仅用于 `routingPlan == null` 的分支（即非自适应 hybrid）。
因此它**不是** adaptive 质量问题的原因，但仍是不可配置的魔数。

⚠️ 另注：`RecallPlan` 与 `DeterministicRulePolicy.addChannels` 存在**两套并行的预算分配逻辑**，
这是维护风险，但合并超出本次范围（见 §6）。

### 2.4 关联分数公式的硬编码乘数（违反设计对 metadata 的要求）

设计明确要求关联分数的**各分量及其版本**写入 build metadata，但两项并未纳入：

| 常量 | 值 | 位置 |
|---|---|---|
| `UNRELATED_SOURCE_RELEVANCE` | 0.5 | `channel/graph/GraphRetriever.java:47` |
| `ANCHOR_HIT_BASE_SCORE` | 1.0 | `channel/graph/GraphRetriever.java:49` |

影响：`sourceRelevance` 是 `associationScore` 的正式乘数，这两项固定后**分数无法完全复现**，
即使用户设置了 `min-association-score`。

### 2.5 `CASCADE_MIN_PROBE_SCORE_GAP = 0.0001`：量纲可疑

`RecallService.java:104`。实测 `cascadeProbeScoreGap` 中位 `0.00055`，阈值仅差约 5 倍，
取值微调会翻转大量查询的图阶段开关。同时 `merged.size() >= 2` 是裸字面量。

### 2.6 `TEXT_CANDIDATE_CONFIDENCE = 0.35` 与 `strongAnchorConfidence = 0.75` 的隐性耦合

`EntityAnchorResolver.java:50` 的 0.35 **恒小于** `strongAnchorConfidence` 默认 0.75，
意味着纯文本回退锚点永不满足上一轮新增的 `anchored` 判断。此耦合无任何记录。

### 2.7 `DeterministicReranker.graphPathWeight` 默认 0.0 且不可配置

`RetrievalStrategyFactory:40` 使用无参构造。设计要求「图路径质量作为独立特征」，
实际从未启用，也无法调整。

## 3. 实施方案

### 步骤 1：图主导融合权重与探针份额（P0）

`RetrievalProperties` 新增 7 个字段 + 校验 + getter/setter：

```
retrieval.graph-fusion.graph-weight          默认 2.0
retrieval.graph-fusion.text-weight           默认 0.25
retrieval.graph-fusion.probe-share           默认 0.4   （范围 [0,1)）
retrieval.graph-fusion.lexical-bm25-weight   默认 1.25
retrieval.graph-fusion.lexical-vector-weight 默认 0.85
retrieval.graph-fusion.semantic-bm25-weight  默认 0.85
retrieval.graph-fusion.semantic-vector-weight 默认 1.25
```

`DeterministicRulePolicy`：
- 新增接收这些值的构造器重载；保留现有 8 参构造器委托到新构造器（默认值不变）。
- `getParameters()` 加入这 7 项，使 trace 的 `policyParameters` 完整记录。

`RetrievalStrategyFactory.routingPolicy()` 从 properties 读取并传入。

**测试**：`RetrievalPropertiesTest` 校验默认值与非法值；`AdaptiveRoutingTest` 断言
自定义权重确实进入计划与 `getParameters()`。

### 步骤 2：`rrfRankConstant` 配置化（P0）

`RetrievalProperties` 新增 `retrieval.rrf-rank-constant`（默认 60，范围 ≥1）。
构造生产 `WeightedRrfConfig` 时使用该值，而不是 `WeightedRrfConfig.DEFAULT`。

**顺带修复一个真实缺陷**：`RecallService.isDefaultFusionConfig()` 只比较三个权重，
却在 `RecallService:650-655` 用它决定是否**整体覆盖**路由计划的权重。
该判断应同时考虑 `rankConstant`，否则一个仅改了 `rankConstant` 的配置会被静默忽略。

**测试**：断言自定义 `rankConstant` 进入 `trace.rrfRankConstant` 且生效。

### 步骤 3：关联分数乘数进入 metadata（P1）

`AssociationScoreMetadata` 增加两个字段 + 版本号：
- `unrelatedSourceRelevance`（默认 0.5）
- `anchorHitBaseScore`（默认 1.0）

`GraphRetriever` 从 config 读取而非静态常量；`GraphRetrievalConfig` 增加对应 setter 与校验。
`MetadataJson` 编解码保持 legacy 兼容（缺失字段回落默认值并标注）。

**测试**：`AssociationScoreMetadataTest` 断言往返与 legacy 缺省；
`AssociationScoreFormulaTest` 断言乘数进入 `sourceRelevance` 计算。

### 步骤 4：级联门控可配置化（P1）

`RetrievalProperties` 新增：
```
retrieval.cascade.min-probe-score-gap   默认 0.0001
retrieval.cascade.min-probe-evidence    默认 2
retrieval.cascade.min-budget            默认 5
retrieval.cascade.probe-max             默认 10
retrieval.cascade.probe-min             默认 2
retrieval.cascade.probe-divisor         默认 8
```

`RecallService` 用配置值替代 `CASCADE_MIN_PROBE_SCORE_GAP` 与字面量 `2`；
`RecallPlan` 通过构造器接收而非静态常量。

**测试**：阈值边界 + trace 记录实际求值的阈值。

### 步骤 5：隐性耦合显式化（P2）

在 `EntityAnchorResolver.TEXT_CANDIDATE_CONFIDENCE` 的 Javadoc 中明确说明它与
`strongAnchorConfidence` 的关系，并在 `RetrievalProperties.validateConfiguration()` 中加入
一致性校验：若 `strongAnchorConfidence <= TEXT_CANDIDATE_CONFIDENCE`，记录 WARN 到
`policyParameters`（不抛异常，避免破坏既有配置）。

### 步骤 6：reranker 图路径权重可配置（P2）

`RetrievalProperties` 新增 `retrieval.reranker.graph-path-weight`（默认 0.0）。
`RetrievalStrategyFactory.reranker()` 传入该值。保持默认 0.0 以不改变现有结果。

## 5. 风险

| 风险 | 缓解 |
|---|---|
| 新增 13+ 配置项导致 `RetrievalProperties` 膨胀 | 按用途分组命名（`graph-fusion.*` / `cascade.*` / `rrf-*`）；校验集中在现有 `validateConfiguration()` |
| 改动 `isDefaultFusionConfig` 可能改变既有行为 | 该判断当前只影响「显式设置非默认融合配置」的调用方；新增 `rankConstant` 比较不会改变默认路径 |
| `AssociationScoreMetadata` 加字段影响 legacy 解码 | 严格遵循现有模式：缺失 → null/默认，不臆造，`MetadataModelTest` 已有先例 |
| 配置化后默认值算错导致 benchmark 漂移 | §4 的逐位比对是硬门槛 |

## 6. 非阻塞开放问题

1. **`RecallPlan` 与 `addChannels` 双套预算逻辑**（§2.3）建议后续合并为单一来源，但会改变
   非自适应 hybrid 的行为，需单独评估，本次不动。
2. **`preserveTopKChannel` 只保召回不参与重排**：这是 Adaptive 仍未追平 Graph-only 的残余原因
   （2Wiki MRR 0.4747 vs 0.5445）。是否让文本权重在锚点可靠时趋近 0，需产品决策，本次不动。
3. `CASCADE_MIN_PROBE_SCORE_GAP` 的合理取值需要 ablation 实验确定，本次仅配置化并保留现值。

## 7. 已否决的备选方案

- **直接删除 `CASCADE_*` 常量**：会导致非自适应 hybrid 的预算逻辑失效，且 adaptive 在
  `routingPlan == null` 时仍需回退。
- **把 `GRAPH_FIRST_TEXT_WEIGHT` 直接设为 0**：等价于退回 graph-only，Adaptive 失去存在意义。
- **用 `@Value` 注解替代 `@Inject`**：与仓库现有 `RetrievalProperties` 风格不一致。
- **为每个常量单独建类**：过度设计，13 个标量不值得。

## 8. 执行中发现的关键偏差（2026-11-04）

### 8.1 生产路径根本不读 `RetrievalProperties`

**事实**：`RetrievalService.retrieve()` 第 103 行构造服务时用的是
```java
new RecallService(fixtureRegistry)
```
即**不带 properties 的构造器**，其内部走：
```java
this(registry, WeightedRrfConfig.DEFAULT, ..., new DeterministicRulePolicy(), 1, true, null, null);
//                                                                                  ^^^^ properties = null
```

后果：`RetrievalProperties` 里所有 `retrieval.deterministic-rule.*`、
`retrieval.graph.*` 配置在**生产 HTTP / benchmark 路径上全部无效**；
`DeterministicRulePolicy()` 用的是一组硬编码构造器默认值。

**这解释了上一轮的困惑**：把 `high-score-gap` 默认值从 `0.20` 改成 `0.0005` 后，
benchmark 结果**完全不变**——因为那个值根本没被读到。

### 8.2 对计划的影响

原计划 §3 只做"配置化"，但若不同时修复装配，配置化在生产上等于无效。
因此新增 **步骤 0（前置修复）**：让 `RetrievalService` 用 `properties` 装配 `RecallService`。

这属于计划 §1「保持默认值不变」范围内的修复：修复后应读取到与
`DeterministicRulePolicy()` 无参默认值**一致**的配置值，故 benchmark 数字仍应逐位复现。

**风险**：一旦接通，之前被忽略的配置（如 `graph.sample-rate`、`min-association-score`）
会真正生效，可能暴露新的行为差异。§4 的逐位比对就是检验手段。

### 8.3 验收调整

新增验收项：`RetrievalService` 装配后，`trace.policyParameters` 中的权重值必须等于
`RetrievalProperties` 中的配置值（而非策略类硬编码默认值）。

### 10.1 补齐过程中发现并修复的真实缺陷

**`DeterministicRulePolicy.addChannels` 在 replan 预算耗尽后仍重排预算**

`afterText` 分支未检查 `replanExhausted`，导致策略达到 `maxReplanCount` 后仍把预算改成
1/1/98——正是该上界要防止的循环。已加 `&& !replanExhausted` 守卫，由
`ReplanBoundTest.exhaustedReplanBudgetKeepsTheInitialDecision` 锁定。

**跨语言 relation path 语义不一致（已记录而非静默）**

Java `relationPathHit` 用**整标签集合成员判断**，Python `_contains_sequence` 要求**完整序列连续匹配**。
同一输入可得到 1.0 vs 0 的不同结果。fixture 现同时记录 `javaRelationPathHit` 与
`pythonRelationPathHit` 两列，并由 `fixtureRecordsWhereJavaAndPythonDisagreeOnGranularity`
断言差异被保留，避免两份报告静默打架。
