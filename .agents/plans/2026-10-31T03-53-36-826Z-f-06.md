# 补齐 F-06 自适应路由与重规划的缺口

## 1. 目标与假设

PR F-06 (`tmp/graphrag/MVP2Full/pr-f06-adaptive-routing-and-replanning.md`) 的骨架（RoutingPolicy SPI、RoutingFeatures、DeterministicRulePolicy、RetrievalPlanValidator、RetrievalReplanEvent）已实现且 `AdaptiveRoutingTest` 通过，但文档点名的若干验收要求只是"字段存在、值恒为默认/空"。本计划把这些**语义空洞**补成真实行为。

假设：
- 不改 Graph backend、不加 HTTP endpoint（F-07 范围）。
- 不引入学习型策略，只把 `DeterministicRulePolicy` 做对。
- F-05 遗留的 `BudgetLedger.tryEvaluateCandidate` 死代码与 `maxReplanCount` 循环问题**合并到本计划一并修**，因为 F-06 的 replan 正确性依赖它。
- 检查通过口径：`mvn -o -pl geaflow-ai -Djacoco.skip=true test`，Checkstyle 四空格 / 200 列。

## 2. 排查结论：缺口清单

全部缺口均已用 `grep` 证实，非推测。

### G1. `RetrievalReplanEvent.adjustments` 永远是空列表 —— 严重

`execution/RetrievalReplanEvent.java:44` 有完整 `adjustments` 字段，`getAdjustments()` 在第 105 行暴露，但**全仓唯一构造点** `service/RecallService.java:621` 传入 `null`，`getAdjustments` 在 `src/` 内无任何读取者。

文档要求：「校验调整要进入 trace」「非法 plan 被 executor **修正**或按配置 typed reject」。当前 `RetrievalPlanValidator.validate()` 只 `throw invalid(...)`，没有"修正 + 记录调整"分支，所以"修正"路径完全缺失，`adjustments` 恒空。

### G2. `unusedCandidates` / `unusedTokens` 与 `remaining*` 恒等 —— 语义错误

`RecallService.java:621` 附近把 `progress.getRemainingCandidates()` 同时喂给 `remainingCandidates` 和 `unusedCandidates`（token 同理）。文档要求分别记录「剩余预算**和**未使用预算」，现在两个字段永远同值，无法区分"预算没用完"和"plan 分出去的配额没花完"。

### G3. `maxReplanCount` 只作 `> 0` 门控，replan 无循环 —— 配置失效

`RecallService.java:613`：
```java
if (maxReplanCount > 0 && !expired(deadline)) { ... }
```
`maxReplanCount=1` 与 `=5` 行为完全相同；`RetrievalProgress.replanCount` 被填充（`RecallService:307`）但**策略从不读取**（`getReplanCount` 全仓无调用者）。文档要求「不超过 maxReplanCount」在单轮下侥幸成立，但多阶段边界的 replan 能力实际不存在。

### G4. 初始 `RoutingContext` 两个关键特征恒为默认值 —— 决策失真

`RecallService.routingContext()`（约 194–230 行）只填了 `queryLength`、`averageIdf`、`anchorCount`、`anchorConfidence`、`candidateDegree`。**`firstStageScoreGap` 和 `graphGrowthRate` 未设置（均为 0.0）**。

后果：初始 plan 中 `graph = hasIndex(GRAPH) && growthRate(0) <= highGrowthRate` **恒为 true**，`GRAPH_STOPPED_GROWTH` 这条规则在初始规划中永远不触发；`graphMaxHop`/`neighborCap`/`channelBudget` 全部基于失真特征分配。文档要求「扩散过快时停止 graph」，实际只有 replan 之后才可能生效。

### G5. `RoutingFeatures.SCHEMA_VERSION` 未落 trace 的初始路径 & 特征快照不完整

`trace.routingFeatures` 由 `RetrievalResponseValidator.validateAdaptiveTrace` 强校验必须与 `RoutingFeatures.empty().asMap().keySet()` 完全一致（7 个键全非负）。G4 导致其中 2 个键恒为 0 但"合法"，校验器无法发现失真。需要在补 G4 的同时确保快照记录的是**实际用于决策的特征**，且 replan 后的特征单独可回溯。

### G6. `RetrievalPlan` 的 `maxDiffusionGrowth` / `hardUpperBounds` 未被校验器与执行器一致使用 —— 中等

`RetrievalPlan.maxDiffusionGrowth` 由策略设置（`highGrowthRate`），`RetrievalPlanValidator` 只校验它是有限值或 `+Inf`，但 `RecallService` 执行 graph 阶段时**没有用它作为扩散停止阈值**（实际停止依赖 `RecallStopReason.EDGE_SCAN_LIMIT`/`CANDIDATE_LIMIT`）。文档「扩散过快时停止 graph」「校验…fallback 和硬上限」要求 plan 里的这个阈值真正生效。

### G7. `DeterministicRulePolicy` / `maxReplanCount` 未暴露为配置 —— 中等

`config/RetrievalProperties.java` 中 `grep routingPolicy|RoutingPolicy|maxReplan` 无命中。策略、阈值、`maxReplanCount` 只能走 `RecallService` 构造器；生产默认写死 `new DeterministicRulePolicy(), 1`（`RecallService:331-332`）。文档要求「暴露 policyId、policyVersion、policy parameters」——参数已进 trace，但无法运维侧调整，且 F-05 的 `Reranker`/`TokenEstimator` 同样未配置化。

### G8. 无 replan 的负向测试

`AdaptiveRoutingTest` 6 个测试覆盖了策略与校验器，但**没有**测：replan 次数上限、replan 只在配置边界发生、不得中断正在执行的 candidate operation、非法 plan 的 typed reject 落到 trace。文档"测试与验收"第 3、4 条无对应用例。

### G9.（F-05 遗留，本计划顺带）`BudgetLedger.tryEvaluateCandidate` 死代码

全仓无调用者，`getCandidatesEvaluated()` 恒为 0；candidate 约束实际由 reader 层 `candidateBudget` 参数强制。导致账本无法回答"共评估多少候选"，`RetrievalProgress.remainingCandidates` 改用 `trace.getEvaluatedCounts()` 求和绕过账本。

## 3. 实施步骤

按依赖顺序，每步可独立编译通过。

### 步骤 1 — 校验器支持"修正并记录"（解决 G1）

文件：`execution/RetrievalPlanValidator.java`、新增 `execution/PlanAdjustment.java`

- 新增不可变记录类 `PlanAdjustment`：
  - `field`（如 `channelBudget.GRAPH`、`maxHop`、`fallbackMode`）
  - `from`、`to`（String 形式，便于进 trace JSON）
  - `reason`（如 `CLAMPED_TO_HARD_UPPER_BOUND`、`DROPPED_UNAVAILABLE_CHANNEL`、`CLAMPED_MAX_HOP`）
- 新增 `RetrievalPlanValidator.Result`（`plan` + `List<PlanAdjustment> adjustments`）。
- 新增 `validateAndAdjust(plan, context)`：对**可安全收敛**的违规做修正而非抛异常，并记录 adjustment：
  - `channelOrder` 含不可用 index → 移除该 channel，同步移除其 budget，若因此不再满足 HYBRID 则降级 `selectedMode` 为对应单通道 mode 并记 reason。
  - `maxHop > context.maxHop` → clamp。
  - `neighborCap > candidateBudget` → clamp。
  - channel budget 之和 > `candidateBudget` → 按比例 clamp 最后一个 channel。
  - 触碰硬上限（`candidates`/`tokens`/`latencyNanos`/`maxHop`）→ clamp 并记 reason。
- 保留现有 `validate(plan, context)` 作为**严格模式**（typo/结构性错误仍抛 `RetrievalErrorCode.INVALID_REQUEST`），供配置开关 `strictPlanValidation=true` 时使用。
- 判定标准：结构性错误（未知 channel、未知 upper bound key、权重全零、`topK > candidateBudget`）继续 reject；数值/可用性问题走 adjust。

### 步骤 2 — 真实 unused 预算（解决 G2）

文件：`service/RecallService.java`（replan 段，约 600–630 行）

- 在构造 `RetrievalReplanEvent` 前计算：
  - `unusedCandidates = Math.max(0, oldPlan.getChannelBudget 已分配之和 - candidatesUsed)`
  - `unusedTokens = Math.max(0, oldPlan.getTokenBudget() - tokensUsed)`
  - 复用 `routingProgress` 已有的 `candidatesUsed` / `tokenUsed` 计算逻辑，抽成私有方法 `BudgetUsage usage(trace, plan, ledger)` 避免重复。
- `remaining*` 继续表示"请求级账本剩余"，`unused*` 表示"旧 plan 配额未花完"。两者语义分开。

### 步骤 3 — replan 循环 + 策略可见 replanCount（解决 G3、G8 部分）

文件：`service/RecallService.java`、`execution/RetrievalProgress.java`（无改动，已有字段）

- 将 `if (maxReplanCount > 0 && ...)` 改为循环：
  ```
  int replanCount = 0;
  while (replanCount < maxReplanCount && !expired(deadline) && hasNextStageBoundary()) {
      progress = routingProgress(...) // 用最新 effectivePlan 重算
      Result r = RetrievalPlanValidator.validateAndAdjust(policy.plan(ctx, progress), ctx);
      record event(boundary, ..., r.adjustments, unused...)
      effectiveRoutingPlan = r.plan;
      replanCount++;
  }
  ```
- 边界当前只有 `AFTER_TEXT`；循环天然只在已声明的阶段边界迭代，**不会**中断执行中的 operation（因为边界判定发生在 `StageExecutor` 完成之后）。
- 保证幂等：若新 plan 与旧 plan 的核心字段（`selectedMode`/`channelOrder`/`channelBudgets`/`maxHop`/`neighborCap`/三个 weight）完全相同，则**不记录 event、不递增 replanCount、跳出循环**，避免 `maxReplanCount` 被空转耗尽。
- `RetrievalProgress.replanCount` 传当前 `replanCount` 而非 `trace.getReplanEvents().size()`。

### 步骤 4 — 初始特征补全（解决 G4、G5）

文件：`service/RecallService.java`（`routingContext`，约 194–230 行）

- `graphGrowthRate` 初始值改为从 `provider.getStatistics()` 计算的初始估计（若统计不可用则显式 `0.0` 并在 `routingReasons` 记 `GRAPH_GROWTH_UNKNOWN_INITIAL`）。
- `firstStageScoreGap` 初始值：在 `routingContext` 阶段尚无可用的 probe 结果，显式 `0.0`，但**必须**在 `trace.routingReasons` 记 `FIRST_STAGE_SCORE_GAP_UNMEASURED`，让审计可区分"真的是 0"和"尚未测量"。
- `trace.routingFeatures` 改为记录**最终 effective plan 所依据的特征**（replan 后取 `progress` 合并特征），并把初始特征单独写入 replan event（已有 `oldPlan` 路径）。若 `maxReplanCount=0`，则记录初始特征。
- 保证 `RetrievalResponseValidator.validateAdaptiveTrace` 的 7 键校验仍通过。

### 步骤 5 — `maxDiffusionGrowth` 真正生效（解决 G6）

文件：`service/RecallService.java`（graph 阶段执行处）、`execution/RecallStopReason.java`（复用 `GRAPH_STOPPED_GROWTH` 或已有 `EDGE_SCAN_LIMIT`）

- 在 graph 扩展循环内，用 `effectiveRoutingPlan.getMaxDiffusionGrowth()` 作为阈值：当实时 `growthRate` 超过阈值时停止，`channelStopReasons.put("GRAPH", RecallStopReason.GRAPH_STOPPED_GROWTH)`。
- 若 `RecallStopReason` 无该枚举值，新增 `GRAPH_STOPPED_GROWTH`（检查是否已存在，F-05 清单里未见，需新增）。
- `trace.graphGrowthRate` 继续记录实测值，便于验证阈值触发。

### 步骤 6 — 配置化策略与预算（解决 G7，含 F-05 顺带项）

文件：`config/RetrievalProperties.java`、`service/RecallService.java`（工厂方法）

- 新增可选项：
  - `routingPolicyId`（默认 `deterministic-rule`）
  - `maxReplanCount`（默认 `1`，保持现状行为）
  - `strictPlanValidation`（默认 `true`，保持现状行为）
  - 阈值 8 项（`highAverageIdf`、`highScoreGap`、`longQueryLength`、`strongAnchorConfidence`、`minimumAnchorCount`、`highCandidateDegree`、`highGrowthRate`、`baseNeighborCap`）——以 `deterministic-rule.*` 前缀
  - `rerankerId` / `tokenEstimatorId`（默认 `deterministic-reranker` / `chars4`），为 F-05 预留
- `RecallService` 增加 `static RecallService fromProperties(...)` 工厂，按 id 解析实现，未知 id 抛 `INVALID_REQUEST`。
- 保留现有构造器（测试在用，`AdaptiveRoutingTest`/`ExecutionBudgetTest` 依赖）。

### 步骤 7 — 补测试（解决 G8）

## 5. 风险与非阻塞疑问

**风险**

- R1：步骤 1 的"修正"会改变现有行为——原本抛异常的非法 plan 现在可能被静默修正。缓解：默认 `strictPlanValidation=true`，`validateAndAdjust` 仅在 replan 路径启用（初始 plan 仍走严格校验），这样 F-06 只影响自适应部分，接口不变。
- R2：步骤 3 的循环可能因策略在边界间反复返回不同 plan 而多花请求预算。缓解：幂等短路（步骤 3 末段）+ `maxReplanCount` 硬上限 + `expired(deadline)` 检查。
- R3：步骤 4 把 `graphGrowthRate` 从"恒 0"改为真实值，会让某些此前选中 graph 的请求不再选中 graph，可能改变 `GraphRagMvpEndToEndTest` 期望。缓解：先在测试中断言并显式调整期望，视为**修正后的正确行为**，在 PR 描述里记录这项行为变更。
- R4：步骤 5 新增枚举值会扩展 `RecallStopReason` 的 JSON 取值面，若下游有白名单需同步。缓解：先检查 `RetrievalApiJson` 与 validator 是否对 `channelStopReasons` 做枚举白名单校验。
- R5：步骤 6 新增配置项若被 `RetrievalPropertiesTest` 的严格字段测试覆盖（存在 `unknown property` 拒绝逻辑），需同步更新该测试。

**非阻塞疑问（不阻塞开工，按推荐默认执行）**

- Q1：`deterministic-rule.*` 阈值是否需热更新？默认按"启动时读取一次"实现，不引入动态配置。
- Q2：`unused*` 是否需要累加多轮 replan 的全部未使用量？默认每轮 event 各记各的，不做汇总字段。
- Q3：是否顺带修 G9（`tryEvaluateCandidate`）？默认**修**：在 `RecallService` 打分循环里对每个新候选调用 `ledger.tryEvaluateCandidate()`，若账本拒绝则跳过；`getCandidatesEvaluated()` 由此变的真实。若认为超出 F-06 范围可拆成独立 PR。

## 6. 已拒绝的方案

- **用 `subList` + 事后排序代替 replan 循环**：不解决 `maxReplanCount` 失效，且无法在边界重算 `remaining*`。
- **把 `adjustments` 改为从 `oldPlan`/`newPlan` 差异自动 diff 生成**：无需改 validator，但无法表达"为什么修"（reason），达不到文档"records adjustments"的审计要求。
- **在 `RoutingFeatures` 增加 `firstStageScoreGapMeasured` 布尔字段**：破坏 `routingFeatures` 的 `Map<String, Number>` schema 与 7 键强校验；改用 `routingReasons` 标记更轻量。
- **为 replan 新增独立阶段 `GRAPH_PREFLIGHT`**：超出文档范围（F-06 明确"只在配置的阶段边界"），且会改变 stage 计数影响 F-05 的 `stageElapsedNanos` 契约。

### 9.1 修复 R6：批量扣减替代逐候选加锁

`BudgetLedger.tryEvaluateCandidate()` 是 `synchronized`，原 `chargeEvaluatedCandidates` 对每个候选调一次，
在 `max-candidates: 1000` 下每次请求最多 1000 次加锁，且 `ExecutionMode.PARALLEL` 下跨线程竞争会放大。

新增 `BudgetLedger.tryEvaluateCandidates(int evaluated)`：单次临界区内扣减
`min(evaluated, candidateBudget - candidatesEvaluated)`，返回实际扣减数。
语义与逐个调用完全等价——包括三处副作用：
- 预算耗尽时置 `CANDIDATE_BUDGET`（仅在已扣减数 < 请求数时）；
- `checkDeadline()` 失败时置 `DEADLINE` 并扣减 0；
- `evaluated == 0` 直接返回 0 且不改 stopReason（保留 `COMPLETED`）。
`evaluated < 0` 抛 `IllegalArgumentException`。

`RecallService.chargeEvaluatedCandidates` 改为直接调用批量方法。

新增两个测试固定等价性：
- `batchCandidateChargeMatchesPerCandidateCharge` — 同一 budget 下分批扣减与逐个扣减的
  `charged` 计数、`getCandidatesEvaluated()`、`getStopReason()` 完全一致；
- `batchCandidateChargeRespectsDeadlineAndRejectsNegativeCounts` — 过期 ledger 扣减 0 且记
  `DEADLINE`、负数抛异常、单批不误置 `CANDIDATE_BUDGET`。

`tryEvaluateCandidate()` 保留（`BudgetLedger` 的公开单个 API，`ExecutionBudgetTest` 原有用例仍覆盖）。
